# Bingen meeting prep — gym app lessons

Use this as the process part of the meeting. The point is not to solve the new product today. The point is to agree on how not to repeat the Unit/gym-app mistakes.

## Opening frame

"I want to separate two things: friendship energy and market evidence. With Unit, I started by solving my own problem. That helped me move fast, but it also made me skip research, skip shaping, and spend way too much time building around assumptions. If we cofound something, I want us to protect the friendship by being stricter with the process."

## What went wrong with the gym app

1. **I solved my own problem first.**
   - Good: high motivation, clear personal pain, strong taste.
   - Bad: I treated my own pain as market evidence.
   - Rule for us: personal pain can start a hypothesis, but it cannot validate one.

2. **I did not shape the project enough before building.**
   - I started with "progressive overload app" as the rough idea, but the product surface kept expanding.
   - Core concepts were still moving while I was already coding.
   - Rule for us: no build phase until we have a shaped one-page pitch: problem, buyer, appetite, solution sketch, rabbit holes, no-gos, kill criteria.

3. **I confused MVP with too much product.**
   - The first version tried to carry too many future-product assumptions.
   - Some core features were started, then abandoned or redesigned mid-build.
   - Rule for us: start with an `SLC`, not a bloated MVP.

4. **I did not define hard no-gos early.**
   - Progressive overload, planning, logging, coaching, analytics, and habit loops all tried to enter the same product.
   - Rule for us: every hypothesis needs a visible "not building this now" list.

5. **I let building teach me what shaping should have taught me.**
   - That made the build phase 10x longer than it needed to be.
   - Rule for us: uncertainty belongs in research and shaping, not in production code.

6. **I did not create a clean learning loop after each phase.**
   - Context stayed in my head or in scattered chats instead of becoming reusable project memory.
   - Rule for us: after every research/build/posting cycle, we write the lesson into the repo so Claude/Codex and both founders carry the same context forward.

## The term I was trying to remember

**SLC = Simple, Lovable, Complete.**

Use this instead of "MVP" when deciding what to ship first.

- **Simple**: small enough to build without dragging future scope into v1.
- **Lovable**: has one sharp moment users actually care about, not just a technically working shell.
- **Complete**: the narrow promise is fully usable end to end.

For us: the first product should not be "the smallest broken version of a big vision." It should be the smallest complete version of one painful job.

## Process rules to propose

1. **Hypothesis before product.**
   - We write the pain, persona, current workaround, WTP signal, and kill criteria before naming features.

2. **Research before building.**
   - Minimum bar: 10 real complaints, from distinct people, with at least 3 clear willingness-to-pay signals.
   - If we cannot find them, we kill or reframe the idea.

3. **Fixed appetite, flexible scope.**
   - Each hypothesis gets a fixed time budget: usually 1 week.
   - When time is up, we decide: kill, continue, or post for testers.

4. **No mid-build reshaping.**
   - If the core product changes during build, we stop and reshape.
   - We do not keep coding while the definition keeps moving.

5. **One active bet at a time.**
   - No parallel maze of Unit + Blocker + Eclipta + new cofounding app unless we explicitly choose that tradeoff.

6. **Document decisions immediately.**
   - Use `notes/decisions.md` for joint calls.
   - Use `notes/conflicts.md` when we disagree and need a 24-hour cooling period.
   - Use `notes/graveyard.md` when an idea dies, so we do not resurrect it emotionally.

## What to ask Bingen

1. "When you built Eclipta, where did you shape first, and where did you discover the shape while building?"
2. "What is the biggest mistake you made building it solo?"
3. "If we worked together, what process would make you trust that we are not just chasing friendship energy?"
4. "Would you rather validate a new problem together, or run a strict growth process around Eclipta first?"
5. "What would make you kill a cofounding idea even if we both liked it?"

## Suggested meeting outcome

Do not leave with a product decision. Leave with a process decision.

Best outcome for this meeting:
- We agree personal pain is not enough.
- We agree to use SLC as the v1 bar.
- We agree every idea needs kill criteria before build.
- We agree whether the next bet is Eclipta growth, a fresh validated problem, or just a private friendship/build protocol.
